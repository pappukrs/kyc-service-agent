# KYC Servicing Agent

An **AI-assisted customer-servicing agent for retail-banking onboarding and KYC**, built as a
production-shaped system rather than a demo: typed tools behind an **MCP server**, a **LangGraph**
agent loop, human-in-the-loop approval on every write, an append-only audit trail, and an
evaluation suite that runs in CI.

> ⚠️ **Synthetic data only.** Every customer, document, and case in this repository is generated by
> `scripts/seed.py`. No real customer data, no real PII, no production credentials — by design.

---

## What it does

A servicing request arrives — *"why was my KYC document rejected?"*, *"what's blocking my
onboarding?"*, *"update my registered address"* — and the agent resolves it end to end: resolves the
customer, reads their onboarding and KYC state, explains the blocker in plain language, and either
answers directly or opens a servicing case. Anything that **writes** pauses for human approval.

## Architecture

```
                    ┌──────────────────────────────────────────┐
   HTTP  ─────────▶ │  FastAPI  —  auth, intake, session        │
                    │  routing, /healthz, /metrics              │
                    └────────────────────┬─────────────────────┘
                                         │
                    ┌────────────────────▼─────────────────────┐
                    │  Agent  —  LangGraph loop                 │
                    │  plan → call tool → observe → repeat      │
                    │  interrupt() before any write             │
                    └────────────────────┬─────────────────────┘
                                         │ tools loaded over MCP
                    ┌────────────────────▼─────────────────────┐
                    │  MCP server  —  the ONLY path to data.    │
                    │  7 typed tools, read/write split.         │
                    └───────┬───────────────────────┬──────────┘
                            │                       │
              ┌─────────────▼──────────┐   ┌────────▼─────────────┐
              │  MongoDB               │   │  Kafka               │
              │  customers             │   │  servicing.tasks     │
              │  kyc_documents         │   │  servicing.audit     │
              │  servicing_cases       │   └────────┬─────────────┘
              │  conversations         │            │
              │  tool_audit (append)   │   ┌────────▼─────────────┐
              │  idempotency_keys      │   │  Worker — async doc  │
              └────────────────────────┘   │  verification        │
                                           └──────────────────────┘
```

**The core design decision: the agent has no direct database access.** Every capability is a typed
MCP tool with an explicit contract. That is what makes the audit trail complete, the permission
model enforceable, and the agent framework swappable — the same tool surface runs under LangGraph
and under Google ADK.

## Tool surface

Seven tools, split by blast radius. **The read/write split is the security boundary.**

| Tool | Kind | Contract |
|---|---|---|
| `get_customer` | read | `customer_id` → profile, onboarding stage, risk tier |
| `get_onboarding_status` | read | `customer_id` → stage, blockers, pending items |
| `list_kyc_documents` | read | `customer_id` → documents with status + rejection reason |
| `search_servicing_kb` | read | `query` → policy / FAQ snippets |
| `verify_kyc_document` | async | `document_id` → enqueues a Kafka task, returns `{status: "queued"}` |
| `create_servicing_case` | **write ⚠️** | requires human approval |
| `update_customer_contact` | **write ⚠️** | requires human approval |

**There is deliberately no money-movement tool.** No transfers, no payments, no balance mutation.
An agent that can move money is a different risk conversation; the scope here is servicing, and the
tool surface enforces that rather than relying on the prompt.

## Stack

Python 3.12 · FastAPI · LangGraph (LangChain) · MCP (`FastMCP` + `langchain-mcp-adapters`) ·
MongoDB (Motor) · Kafka (aiokafka) · Prometheus · Docker Compose

The model provider sits behind a single factory in `src/agent/llm.py` and one config value — the
agent only ever talks to tools, so swapping providers touches one function.

## Quick start

```bash
cp .env.example .env          # fill in your model provider + key
docker compose up -d          # MongoDB + Kafka
uv sync                       # or: pip install -e ".[dev]"
python -m scripts.seed        # ~50 synthetic customers
uvicorn src.api.main:app --reload
curl localhost:8000/healthz
```
